# Память агента: папки проектов и формат файлов

Общий контракт для навыков `rusender-agent`, `rusender-preflight` и `rusender-results`. Файл
одинаковый во всех трёх — навыки ставят по отдельности, общей папки у них нет.

**Версия схемы: 2.** Встретил файл с другой версией — не ломай его молча, скажи человеку.

## Где лежит

```
projects.live/       ← боевые данные, если папка есть. В git не попадает
projects/            ← демо-набор, поставляется с агентом
```

**Правило одно: есть `projects.live/` — работаем в ней, нет — в `projects/`.** Никаких
переключателей и переменных окружения. Скажи вслух, в какой папке работаешь, при первом действии в
диалоге: перепутать боевой аккаунт с демо — дорогая ошибка.

Внутри — по папке на проект:

```
projects/<slug>/
  PROFILE.md       контекст: продукт, аудитория, тон, отправитель, запреты, частота
  lists.md         метаданные списков и сегментов — БЕЗ контактов
  history.jsonl    по строке на кампанию: метрики
  notes.md         наблюдения и гипотезы со статусом
  log.md           что агент делал по проекту, по строке на действие
  letters/         тексты отправленных писем, по файлу на рассылку
  templates/       HTML-шаблоны
  reports/         сгенерированные отчёты
```

`<slug>` — латиница, цифры и дефис. Он же в поле `slug` профиля, он же в `project` строк истории.

Нет папки — памяти нет. Это нормальное первое состояние, а не ошибка: предложи bootstrap и работай
без контекста, пока человек не согласится.

## Что в память класть нельзя

**Никаких персональных данных подписчиков: email-адресов, имён, телефонов, значений переменных
контактов, поимённых списков открывших и кликнувших, SMTP-ответов по конкретным адресам.**

Это не перестраховка. Папки проектов попадают в git, в бэкапы и, если человек делится агентом, в
архив. Так утекают клиентские базы.

Агенту контакты и не нужны: всё, что он делает, он делает через ESP, который и так их хранит. В
памяти живут **метаданные**: имя списка, id, размер, когда собран, какие в нём переменные, по каким
условиям собран сегмент.

Тема письма, имя кампании и текст рассылки — можно: это ваш собственный контент.

**Отдельно про ссылки.** Отчёт по кликам возвращает URL целиком, а в них бывают персональные
данные: на живом аккаунте встретился клик по
`https://…/fd3f5gc52?r=2&email=<адрес получателя>&utm_source=email…`. Такой URL нельзя записывать
в историю, отчёты и лог как есть.

Перед записью вычищай из URL параметры, похожие на персональные: `email`, `e-mail`, `mail`, `phone`,
`tel`, `user`, `uid`, `token`, `hash`, а также любое значение, похожее на адрес электронной почты.
Ставь на их место `<removed>` и сохраняй остальное — путь и UTM-метки для разбора и так достаточны.

Если человеку всё-таки нужны сырые выгрузки под рукой, для них есть `projects/<slug>/private/` —
эта папка в `.gitignore` и не попадает в релиз. Агент туда ничего не пишет сам и не читает оттуда
без прямой просьбы.

## PROFILE.md

Фронтматтер для машины, проза под ним для модели. Обязательны только `slug` и `name` — остальное
доращивается по мере того, как человек рассказывает о проекте.

```markdown
---
schema: 2
slug: shop-rosa
name: "Роза — доставка цветов"
language: ru
esp: rusender
sender:
  id: 41
  email: news@rosa.example
  from_name: "Роза"
domain: rosa.example
folder_id: 10
list_pattern: "| Роза"
default_templates: [2317]
utm:
  source: email
  medium: rusender
  campaign_from: name
frequency_cap:
  sends: 2
  days: 7
updated: 2026-09-23
---

## Продукт
## Аудитория
## Tone of voice
## Чего писать нельзя
## Типовые сегменты
## Ритм и ограничения
```

### Поля

| Поле | Зачем | Если пусто |
|---|---|---|
| `slug`, `name` | Опознание проекта в задаче | Профиль невалиден |
| `demo` | `true` у вымышленных профилей. Запрещает подставлять их id в коннектор | Считай профиль настоящим |
| `language` | Язык писем и отчётов | Считай, что русский |
| `esp` | Какой сервис рассылок у проекта | Считай `rusender` |
| `sender.id`, `sender.email` | Подставить отправителя без вопросов | Спроси и предложи из списка отправителей |
| `sender.from_name` | Имя отправителя обязательно для старта | Возьми из истории кампаний по этому адресу |
| `domain` | Проверка верификации | Возьми из части после `@` |
| `folder_id` | Куда класть кампанию и как отобрать кампании проекта | Отбирай по отправителю |
| `list_pattern` | Подстрока в имени списка, по которой видно проект | Показывай все списки |
| `default_templates` | «Возьми наш стандартный шаблон» | Спроси |
| `utm` | Сверка меток в preflight | Проверку UTM пропусти и скажи об этом |
| `frequency_cap` | Окно для проверки пересечений | Возьми 7 дней, но скажи, что это дефолт |
| `updated` | Когда профиль трогали | — |

**id из профиля — подсказка, а не истина.** Списки пересоздаются, шаблоны удаляются вместе с
кампаниями. Перед использованием проверяй id свежим вызовом коннектора. Не нашёлся — не подставляй
похожий, скажи и спроси.

## lists.md

Метаданные аудиторий проекта. Нужен, чтобы «отправляем активным» превращалось в конкретный id без
похода в ESP и чтобы было видно, как база устроена.

```markdown
---
schema: 2
updated: 2026-09-23
---

## Списки

| id | Имя | Контактов | Создан | Как называем | Переменные |
|---|---|---|---|---|---|
| 42761 | 21.09.26 Активные 90д \| Роза | 42 731 | 2026-09-21 | активные | name, city, last_order_at |
| 42755 | 21.09.26 Спящие 90–365д \| Роза | 18 204 | 2026-09-21 | спящие | name, city |

## Сегменты

| id | Имя | Условия |
|---|---|---|
| 15491 | Активные без платящих \| Роза | contactInList notFindInList 42761 |

## Как пересобирается база

Списки выгружаются из CRM и заливаются заново перед каждой кампанией — id меняются, имена держат
формат `ДД.ММ.ГГ Описание | Проект`.
```

Колонка «Как называем» — самая ценная: она связывает слова человека («активные», «платники») с
реальными id. Без неё агент каждый раз переспрашивает.

## history.jsonl

Одна строка — один снимок метрик одной кампании. JSON без переносов, UTF-8.

```json
{"schema":2,"campaign_id":112538,"project":"shop-rosa","name":"18.09.26 Активные | Сентябрьский дайджест","subject":"Собрали три букета недели","sent_at":"2026-09-18T09:00:00Z","as_of":"2026-09-19T08:12:00Z","audience":{"list_ids":[42761],"segment_id":null,"kind":"active","role":"primary","recipients":42731,"excluded":2108},"delivered":42104,"open":14401,"click":1263,"unsub":97,"complaint":12,"or":0.3421,"ctr":0.03,"ctor":0.0877,"template_id":2317,"letter":"letters/2026-09-18-buket-nedeli.md","tags":["дайджест"]}
```

Правила:

- **Ключ — `campaign_id`.** Повторный сбор статистики по той же кампании **перезаписывает** строку, а
  не добавляет новую. Цифры дозревают неделями, и дубли сделают историю бесполезной.
- `as_of` — когда цифры сняты, `sent_at` — когда рассылка ушла. По разнице видно свежесть снимка.
- `or` = open / delivered, `ctr` = click / delivered, `ctor` = click / open. Доли, не проценты.
  Знаменатель ноль — пиши `null`, а не ноль.
- `letter` — путь к тексту письма в `letters/`, если сохранён. Так история связывается с контентом.
- `audience.kind` — **кому** ушло: `all`, `active`, `paid`, `free`, `churned`, `inactive`, `test`.
- `audience.role` — **чем была отправка в цепочке**. Четыре значения, и это не косметика:

  | role | Что это | Почему отдельно |
  |---|---|---|
  | `primary` | Основная отправка | — |
  | `followup` | Досыл по неоткрывшим | Аудитория по определению та, что не открыла: OR тут в разы ниже |
  | `push` | Дожим по открывшим и кликнувшим | Аудитория по определению вовлечённая: OR в разы выше |
  | `test` | Тестовая отправка | В сравнение не входит никогда |

  **Сопоставимая серия — это одинаковые `kind` И `role`.** На реальном аккаунте смешение ролей
  давало разброс OR от 4,2% до 70,7% в одной «серии»: 4,2% — досыл по неоткрывшим, 70,7% — дожим по
  кликнувшим. Медиана по такому набору не значит ничего.

  **Обе метки назначаются осознанно, а не выводятся из имени списка.** Имена вроде «Платники
  Образование» на вид раскладываются автоматически, но на практике под одну метку съезжают письма
  разных типов. Не уверен — спроси. Держись меток, уже встречающихся в файле; новую заводи, когда
  серия действительно другая.

  Подсказки по именам, если размечаешь пачку задним числом: «досыл», «неоткрывшие» → `followup`;
  «дожим», «открывшие и кликнувшие» → `push`; тип кампании `follow_up_basic` → `followup`. Это
  догадка, а не факт: покажи разметку человеку, прежде чем на ней что-то считать.

Дописывать можно только целыми строками. Строка битая — не чини угадыванием, пропусти и скажи, в
какой строке проблема.

## log.md

Что агент делал по проекту. Append-only, новые записи снизу, по строке на действие.

```markdown
## 2026-09-23
- 14:02 bootstrap — профиль заведён по аккаунту, 3 списка, отправитель 41
- 14:15 rusender-campaign-create — черновик 118902 «Три букета недели»
- 14:16 rusender-preflight — 9 проверок, 1 стоп: {{first_name}} нет в списке 42761
- 14:22 rusender-campaign-create — черновик 118902 обновлён, тема без подстановки
- 14:23 rusender-preflight — 9 проверок, 0 стопов, карточка показана
- 14:31 ЗАПУСК подтверждён человеком — campaigns_schedule 118902
- 2026-09-24 09:40 rusender-results — снимок метрик, OR 31,2%
```

Что писать: время, навык или действие, результат одной фразой, id затронутых объектов.
Что **не** писать: содержимое ответов API целиком, персональные данные, свои рассуждения.

Лог нужен ровно для одного вопроса — «что тут уже делали и чем кончилось». Пиши так, чтобы через
месяц это читалось без расшифровки.

**Запуск рассылки записывай всегда**, отдельной строкой со словом ЗАПУСК. Это единственное
необратимое действие, и след от него должен быть виден сразу.

## notes.md

Наблюдения и гипотезы. Свободная проза, но с обязательным статусом у каждой гипотезы.

```markdown
## Гипотезы

### Короткая тема с конкретной выгодой даёт более высокий OR
- Статус: открыта
- Заведена: 2026-09-18, по кампаниям 112538, 112401, 111980
- Как проверить: следующая рассылка активным с темой до 40 знаков
- Проверка: —
```

Статусы: `открыта`, `подтверждена <дата>`, `опровергнута <дата>`, `отброшена <дата>`. Гипотезу не
удаляй — опровергнутая тоже знание.

## letters/, templates/, reports/

| Папка | Что кладём | Имя файла |
|---|---|---|
| `letters/` | Текст отправленного письма: тема, прехедер, тело | `ГГГГ-ММ-ДД-краткое-имя.md` |
| `templates/` | HTML-шаблоны | `<templateId>-краткое-имя.html` |
| `reports/` | Отчёты, собранные по запросу | `ГГГГ-ММ-ДД-<что>-<id>.html` или `.md` |

Складывать туда всё подряд не надо. `letters/` — те письма, на которые потом будут ссылаться при
разборе («как в прошлый раз»). `templates/` — те шаблоны, которые переиспользуются. Отчёты пишутся
по запросу и живут столько, сколько нужны.

В шаблонах, сохранённых из ESP, остаются `{{переменные}}` — так и оставляй, не подставляй значения.

## Совместное редактирование

Файлы лежат в git и правятся человеком руками. Поэтому:

- перед записью перечитывай файл, а не пиши по памяти из начала диалога;
- не переформатируй чужие строки «заодно»;
- в `PROFILE.md` меняй только те поля, о которых шла речь, и обновляй `updated`;
- в `log.md` только дописывай снизу, никогда не переписывай старые записи.
