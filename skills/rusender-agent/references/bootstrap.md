# Bootstrap: развести аккаунт на проекты

Задача bootstrap — не «создать папки», а один раз разобраться, из чего состоит аккаунт, и записать
то, чего в API нет.

Аккаунт знает, какие есть отправители, домены, папки и списки. Он не знает, что `news@studio.example` и
`hello@atelier.example` — два разных продукта с разной аудиторией, что этим на «вы», а тем на «ты», и что вот
этой базе нельзя писать чаще раза в неделю. Первое достаётся вызовами, второе — вопросами.

## Демо или реальный аккаунт

Первым делом спроси прямо, одним вопросом:

> Завести проекты по вашему аккаунту RuSender — или сначала посмотреть, как это работает, на
> вымышленных примерах?

**Демо.** Работай в `projects/` — там лежит набор из двенадцати демо-проектов, поставляемый с
агентом: магазин, SaaS, школа, клиника, фитнес, медиа, логистика, игра, travel, доставка еды,
бухгалтерия и анонимизированный реальный проект. На демо-профилях работают опознание проекта, написание текста в нужном тоне и
проверка UTM — всё, что не требует живого аккаунта. Отправить по ним ничего нельзя, и это надо
сказать сразу, а не когда человек дойдёт до запуска.

У каждого демо-проекта есть история рассылок, поэтому в демо работают и те проверки, которые без
истории показать нечем: пересечения с недавними отправками и сравнение результата с сопоставимой
серией.

Наборы намеренно разные. В сгенерированных проектах серии однородные — видно, как выглядит
нормальное сравнение. В проекте `rusender`, собранном из настоящего аккаунта, разброс широкий — и на
нём видно, как агент отказывается считать медиану и говорит, что сравнивать не с чем.

Не дописывай в демо-историю результаты реальных кампаний.

**Реальный аккаунт.** Дальше по этому файлу.

## Шаг 1. Собрать сырьё

Пять вызовов, все read-only:

```
senders_list(limit: 100)
domains_list(limit: 100)
folders_list(limit: 100)
lists_list(limit: 100, sortBy: "createdAt", sortDir: "desc")
campaigns_list(limit: 100, status: ["completed"])
```

Списков и кампаний может быть много сотен. Первой страницы достаточно, чтобы увидеть конвенции
именования; вторую страницу бери, только если картина не сложилась. Если ответ коннектора большой и
уехал в файл — разбирай его через `jq`, а не втягивай целиком в контекст.

## Шаг 2. Предложить разбивку

Проект опознаётся по трём сигналам. Сильные — первые два.

**1. Домен отправителя.** Самый надёжный сигнал: разные продукты почти всегда пишут с разных доменов.
`news@studio.example` и `hello@atelier.example` — заведомо разные проекты. Несколько адресов на одном домене
(`info@`, `team@`, `noreply@`) — почти всегда один проект с разными ролями адресов.

**2. Суффикс в имени списка.** Частая конвенция — `ДД.ММ.ГГ Описание | Проект`. Если имена списков
устроены так, суффикс после `|` даёт готовые названия проектов и готовый `list_pattern`. Проверь
гипотезу на десятке имён, прежде чем строить на ней разбивку.

**3. Папки кампаний.** Слабее: папки заводят и по продуктам, и по типам писем («Акции», «Праздники»,
«Тесты»). Используй как подтверждение, а не как основу.

Сведи сигналы и **покажи предложенную разбивку таблицей** — проект, отправители, домен, сколько
списков попало, сколько кампаний:

```
Магазин    team@shop.example, info@shop.example   shop.example   47 списков   112 кампаний
Студия    news@studio.example                          studio.example        8 списков    31 кампания
```

И спроси: всё верно, что-то объединить, что-то разделить?

Отдельной строкой покажи, что **не разложилось** — тестовые списки, адреса на бесплатной почте,
разовые выгрузки. Не запихивай их в проекты ради красоты. «Не разложилось: 14 списков с именами вида
«Тест Слава», 3 адреса на gmail» — честнее и полезнее.

Один домен на весь аккаунт — значит проект один. Скажи это и переходи к шагу 3 без таблицы.

## Шаг 3. Спросить то, чего в API нет

По каждому подтверждённому проекту. **Один вопрос за раз**, и не все сразу — если проектов десять,
человек сдастся на третьем.

Разумный порядок: сначала по всем проектам собери минимум (продукт и аудитория одной строкой), потом
предложи дозаполнить остальное по тем, с которыми реально будете работать.

| Спросить | Зачем | Если человек не отвечает |
|---|---|---|
| Что за продукт и кому пишете | Основа для любого текста | Обязательно, без этого профиль бесполезен |
| На «вы» или на «ты», тон | Чтобы письма звучали как ваши | Считай «вы», нейтрально, и пометь как догадку |
| Чего писать нельзя | Самое ценное и самое непроговариваемое | Оставь раздел пустым |
| UTM-метки | Проверка ссылок в preflight | Проверку UTM пропускай, скажи об этом |
| Как часто пишете этой базе | Окно проверки пересечений | 2 отправки за 7 дней, и пометь как дефолт |
| Стандартный шаблон | «Возьми наш обычный шаблон» | Подскажи по последним кампаниям проекта |

**From Name не спрашивай — достань.** Возьми `campaigns_list(limit: 100, status: ["completed"])`,
отфильтруй по адресу отправителя проекта и посмотри `senderName` свежих кампаний. Самое частое
предложи: «В прошлых письмах с этого адреса имя отправителя было `uKit`. Оставляем?» Так же —
`default_templates` из `templateId` последних кампаний.

## Шаг 4. Записать

Боевые профили заводятся в **`projects.live/`** — эта папка в `.gitignore` и не попадает ни в
коммиты, ни в релиз. Демо-набор живёт в `projects/` и коммитится.

На каждый подтверждённый проект создай папку по формату из `data-layout.md`:

```
projects.live/<slug>/
  PROFILE.md     обязательно
  lists.md       сразу, из lists_list — id, имена, размеры, переменные
  log.md         первая строка: «bootstrap — профиль заведён»
  history.jsonl  пустой
  notes.md       пустой
  letters/  templates/  reports/    пустые
```

Slug — латиницей, короткий: `shop-rosa`, `saas-taskly`, `school-lingvo`.

Чего человек не сказал — **оставь пустым или не пиши поле вовсе**. Пустое поле честно, выдуманное
опаснее пустого: в следующем диалоге его прочитают как факт.

Что помечено догадкой — пометь и в файле, прямо в прозе: «тон: нейтральный, на «вы» (предположение,
не подтверждено)».

Заодно запиши `ACCOUNT.md`: домены с их статусом верификации, подтверждённые отправители, дата
сверки. Это снимок для быстрых ответов, а не источник истины — перед использованием id всё равно
сверяй с коннектором.

`lists.md` заполни сразу — это дёшево и сильно экономит вопросы потом. Колонку «Как называем»
заполняй словами человека: «активные», «платники», «спящие». Именно она связывает задачу с id.
**Контакты не выгружай** — только метаданные списков.

`history.jsonl` при bootstrap **не заполняй**. Есть соблазн вытянуть статистику всех прошлых кампаний
и записать разом, но `campaigns_list(withStats: true)` даёт не тот набор полей, что собирает
`rusender-results`, и получится история из двух несовместимых половин. История наполняется по мере
работы. Если человек хочет заполнить прошлое — это отдельная осознанная задача, и делать её надо
через `rusender-results` по каждой кампании.

## Шаг 5. Показать результат

Коротко: сколько проектов заведено, где лежат файлы, чего в профилях не хватает и что можно
дозаполнить потом. Одной строкой — как этим пользоваться: «Дальше можно говорить «подготовь рассылку
для uKit», контекст подтянется сам».

Не предлагай тут же создать рассылку. Bootstrap — самостоятельная задача, человек пришёл настроить,
а не отправлять.
