# Отправитель, домен, аудитория: проверки до письма

## Две независимые сущности, которые все путают

| Сущность | Где смотреть | Что значит |
|---|---|---|
| **Отправитель** (адрес) | `senders_list` → `verified: "enabled" \| "disabled"` | Человек подтвердил владение конкретным ящиком по письму со ссылкой |
| **Домен** | `domains_list` → `isVerified: true \| false` | В DNS домена прописаны DKIM, SPF, DMARC, и RuSender их видит |

Адрес может быть подтверждён на неверифицированном домене, и наоборот. Для рассылки формально
хватает подтверждённого адреса, но без верифицированного домена письма будут массово падать в
спам у Gmail и Mail.ru. Поэтому проверяй обе сущности и связывай их через `sender.domainId`.

Пример разбора:

```
sender { id: 1001, email: "news@shop.example.ru", verified: "enabled", domainId: 501 }
domain { id: 501, name: "shop.example.ru", isVerified: true }     → рекомендовать
sender { id: 1002, email: "imya.familiya@gmail.com", verified: "enabled", domainId: null }
                                                                  → показать последним, с оговоркой
```

`domainId: null` означает адрес на чужой почте (gmail, mail.ru, yandex, rambler). Такие
отправители работают, но получают худшую доставляемость: DMARC-политика этих провайдеров не
разрешает отправку от их имени через сторонний сервис.

**Домен ищи по имени, а не по `domainId`.** Возьми часть адреса после `@` и найди домен с таким
`name` в `domains_list`. `domainId` у отправителя — всего лишь указатель, и он переживает удаление
домена: в реальном аккаунте встречаются отправители с `domainId`, которого в списке нет, а
`domains_get_by_id` на него отвечает `DOMAIN_NOT_FOUND`. Это не «статус неизвестен», это значит,
что домен из аккаунта удалён или не добавлялся. Так статус верификации виден всегда:

| Что нашлось | Что показать |
|---|---|
| Домен с таким именем, `isVerified: true` | Верифицирован, рекомендуемый отправитель |
| Домен с таким именем, `isVerified: false` | Не верифицирован, покажи какие из DKIM/SPF/DMARC не прошли и что добавить |
| Домена с таким именем нет | Домен к аккаунту не подключён: письма пойдут без вашей подписи. Предложи `domains_create(name)` и верификацию |
| Адрес на gmail, mail.ru, yandex и подобных | Домен подключить нельзя в принципе, это чужая почта |

**Два поля, на которые нельзя опираться.** У отправителя есть `verifiedAt`, и он сплошь и рядом
`null` даже у давно подтверждённых адресов: это не признак того, что адрес не подтверждён.
У домена есть `status: "enabled"`, и он тоже не про верификацию — домен может быть `enabled`
и при этом `isVerified: false`. Судить можно только по `verified` у отправителя и `isVerified`
у домена, всё остальное вводит в заблуждение.

## Как показывать выбор отправителя

Сгруппируй и не заставляй читать сырой JSON:

```
Подтверждённые адреса на ваших верифицированных доменах:
  • news@shop.example.ru (id 1001) — shop.example.ru
  • support@shop.example.ru (id 1005) — shop.example.ru

Подтверждён, но домен не верифицирован:
  • info@partner.example.ru (id 1010) — доставляемость будет хуже

На бесплатной почте (не рекомендуется для массовых рассылок):
  • imya.familiya@gmail.com (id 1002)
```

Если подходящий адрес один — не устраивай выбор, просто скажи, что берёшь его.

## Ветка «нет ни одного подтверждённого отправителя»

1. Спроси адрес, с которого человек хочет отправлять.
2. `senders_create(email)` — сервис отправит на этот ящик письмо со ссылкой подтверждения.
3. Скажи прямо: пока по ссылке не кликнули, адрес в рассылке использовать нельзя. Перепроверить
   можно `senders_list(verified:"enabled")`.
4. Черновик при этом собрать можно — вернёшься к отправителю, когда адрес подтвердят.

## Ветка «нет верифицированных доменов»

Это самая частая причина, по которой у новичка «письма не доходят». Действуй так:

**Домен в аккаунте есть, но `isVerified: false`.** Возьми его `dnsRecords` и выдай записи
таблицей — их нужно добавить в DNS у регистратора или хостера домена:

| Тип | Имя (host) | Значение (data) |
|---|---|---|
| TXT | `mdmdmail._domainkey.example.com` | `v=DKIM1;k=rsa;p=…` |
| TXT | `example.com` | `v=spf1 include:rsndr.ru ~all` |
| TXT | `_dmarc.example.com` | `v=DMARC1; p=none; rua=mailto:…` |

Выводи значения целиком, без сокращений и переносов: DKIM-ключ длинный, но обрезанный ключ
бесполезен. В `dnsRecords` у каждой записи есть свой `isVerified` — покажи, какие уже прошли, а
какие нет, чтобы человек не переделывал готовое.

Что сказать рядом с таблицей:
- записи добавляются в панели того, где обслуживается DNS домена (обычно регистратор или хостер);
- если SPF-запись на домене уже есть, вторую добавлять нельзя — `include:rsndr.ru` дописывается
  в существующую;
- обновление DNS занимает от нескольких минут до нескольких часов;
- после добавления запусти `domains_verify(domainId)` и покажи результат; в ответе бывают
  предупреждения (например, про несколько SPF-записей) и предложенная объединённая SPF.

**Домена в аккаунте нет вообще.** `domains_create(name)` создаёт домен и сразу возвращает
`dnsRecords` — дальше по тому же сценарию. Домен спрашивай тот, на котором ящик отправителя.

Не предлагай `domains_delete`: он работает только для неверифицированных доменов и в сценарии
создания рассылки не нужен.

## Имя отправителя (From Name) из истории

Имя обязательно: без него кампания не стартует. Подбирай так:

1. `campaigns_list(limit:10, status:["completed"])` — ответ отсортирован от новых к старым, и в
   каждом элементе есть `senderId`, `senderEmail`, `senderName`, `startedAt`. Десяти кампаний
   хватает: имя отправителя меняется редко. Не тяни `limit:100` ради одного поля — ответ на сто
   кампаний весит десятки тысяч символов, и коннектор выгрузит его в файл вместо контекста.
   Если это всё же случилось, не читай файл целиком, вытащи нужное:

   ```bash
   jq -r '.data.items[] | "\(.senderEmail)\t\(.senderName)\t\(.startedAt)"' файл.txt | head -20
   ```
2. Отфильтруй по выбранному `senderEmail`. Если по адресу пусто — расширь до домена адреса:
   у одного бренда обычно единое имя на всех ящиках.
3. Возьми самое частое `senderName` среди последних 10–20 кампаний. Если встречаются разные
   варианты, покажи их с числом употреблений и датой последнего: возможно, имя менялось
   осознанно.
4. Предложи найденное как значение по умолчанию, но дай изменить.

Если истории нет, объясни, что имя видно получателю рядом с темой, и хорошее имя — это название
бренда, при необходимости с уточнением («Ромашка», «Марина из Ромашки»). Не сочиняй имя сам.

## Списки, сегменты, переменные

- `lists_list(limit:100, sortBy:"createdAt", sortDir:"desc")` даёт `contactsCount` — этого
  достаточно для выбора. `lists_statistics(listId)` нужен только когда важен разрез по статусам
  контактов (активные, отписавшиеся, ошибки).
- `contacts_statistics()` без `listId` даёт уникальный размер базы. Сумма `contactsCount` по
  спискам его больше: контакт может лежать в нескольких списках.
- `segments_list` — сегмент применяется поверх выбранных списков и сужает аудиторию. Один
  `segmentId` на кампанию.
- `variables_list(listId)` возвращает переменные списка с полем `key` (латиница в нижнем
  регистре). В шаблоне и теме они подставляются как `{{key}}`. Если переменная есть в одном
  списке из трёх — в двух других на её месте будет пусто. Проверяй все выбранные списки прежде,
  чем ставить персонализацию.

## Признаки, о которых стоит предупредить

- Список создан давно, а отправок по нему не было: адреса протухли, доля ошибок будет высокой.
  Предложи поэтапную отправку.
- Больше ~50 000 получателей за раз с домена, который раньше почти не отправлял: репутация
  домена не выдержит. Поэтапная отправка обязательна к обсуждению.
- Пользователь выбирает список, в названии которого есть «парсинг», «купленная», «база из…»:
  скажи один раз, что рассылка по несобственной базе приводит к жалобам и блокировке домена,
  и не превращай это в лекцию.
