# Дашборд транзакционного ключа RuSender

Создавай сводный дашборд по одному ключу отправки на основании данных подключённого RuSender. По умолчанию бери последние 500 писем и точную агрегированную статистику ключа за 30 дней.

## Входные данные

- `key_id` обязателен. Если он не указан, получи список ключей. Выбери автоматически только когда доступен ровно один ключ; иначе попроси пользователя выбрать.
- Размер выборки по умолчанию — 500 последних писем. Если пользователь указал другой размер, используй его.
- Период агрегированной статистики по умолчанию — последние 30 календарных дней.
- Часовой пояс графиков — указанный пользователем; для русскоязычного отчёта без явного выбора используй МСК и подпиши это.
- Язык дашборда совпадает с языком запроса.

## Обязательные правила

- Работай с RuSender только на чтение. Не изменяй ключи, кампании, контакты, домены, шаблоны или настройки.
- Перед расчётами прочитай [references/metrics.md](references/metrics.md). Не придумывай собственные показатели и не называй внутренний статус письма метрикой.
- Перед получением данных прочитай [references/rusender-tools.md](references/rusender-tools.md).
- Для Site-дашборда прочитай [references/dashboard-spec.md](references/dashboard-spec.md), затем используй `sites-building` и `sites-hosting` по их правилам.
- Не сохраняй адреса и имена отправителей/получателей, тело письма, заголовки или другие персональные данные. Для визуализации достаточно ID, времени, статуса и темы письма.
- Не добавляй текстовые выводы, оценки причин, рекомендации или интерпретации. Показывай только данные, формулы и нейтральные подписи.
- Не выводи таблицу всех писем. Это сводка, а не журнал событий.

## Процесс

1. Проверь ключ и получи его имя, статус и домен.
2. Параллельно запроси агрегированную статистику за выбранный период и страницы последних писем с фильтром `keyId`.
3. Останови пагинацию сразу после получения нужного количества писем. Сохрани точный диапазон дат выборки.
4. Удали персональные данные до записи промежуточного JSON или создания Site.
5. Рассчитай стандартные метрики согласно `metrics.md`. Для главных OR и CTR предпочитай независимые агрегированные счётчики `key_stats`.
6. Сгруппируй темы писем по фактическому смыслу. Названия категорий должны описывать конкретный тип уведомления, например «Уведомления о рассылках», «Оплата и тарифы», «Доступ и безопасность». Не называй категорию просто «Рассылки». Нераспознанные темы помещай в «Прочие темы».
7. Объедини повторяющиеся темы, нормализуя только динамические числа, ID и даты. Не объединяй разные по смыслу темы ради красивой таблицы.
8. Собери и опубликуй дашборд. Перед публикацией проверь все пользовательские тексты и формулы как аналитический интерфейс, а не как технический лог.

## Проверка перед выдачей

- OR виден среди главных показателей.
- В блоках по тематикам и повторяющимся темам OR/CTR показаны только там, где их можно корректно восстановить.
- Нет фраз «открыто без клика», «финальный статус: opened», «статус clicked», «вовлечённые письма» и других нестандартных названий.
- У каждого графика понятны объект измерения, единица, период и часовой пояс.
- Основной текст не мельче 16 px; подписи осей и легенды не мельче 14 px.
- В дашборде нет персональных данных и полного списка писем.
