# RuSender: дашборд-отчёт по рассылке (обычной)

## Что делает
По id обычной рассылки собирает всю доступную статистику и публикует единый визуальный отчёт:
итоги, воронку, **динамику открытий по дням**, разбивку по почтовикам, клики по ссылкам и
**панель доставляемости/рисков**. Для A/B-кампаний (`type: ab_basic`) это НЕ тот скилл —
используй `rusender-ab-report`.

## Инструменты (MCP RuSender)
Префикс сервера меняется — загружай по именам через ToolSearch: `public_campaigns_get_by_id`,
`public_campaigns_get_activity`, `public_campaigns_get_stats_by_domains`,
`public_campaigns_get_link_clicks`, при необходимости `public_campaigns_list`.

## Вход
- **id рассылки**. Имя → id через `public_campaigns_list`. Проверь `type`: если `ab_basic` —
  переключись на `rusender-ab-report`; если `follow_up_basic` — см. ниже про досыл.

## Сбор данных
1. **`get_by_id(id, withStats:true)`** — `stats`: total, sending, delivered, open, click, error,
   unsubscribe, complaint. Для `follow_up_basic` дополнительно есть `followUp.stats` (досыл) и
   `totalStats` (основная + досыл) — тогда показывай и досыл, и суммарный итог.
2. **`get_activity(id)`** — открытия и клики по дням → блок «Динамика открытий».
3. **`get_stats_by_domains(id)`** — по Gmail/Yandex/Mail.ru/others: `total`, `open`, `click`,
   `error`, `unsubscribe`, и `iconBase64` (логотипы для вставки как `<img>`).
4. **`get_link_clicks(id)`** — клики в разрезе URL; сгруппируй в понятные категории.

## Метрики
- **OR** = open / delivered; **CTOR** = click / open; **CTR** = click / delivered.
- В разбивке по доменам OR считай как open / total (отправленные группе) — подпиши явно.
- Проценты доставки/ошибок/отписок/жалоб — от отправленных/доставленных; указывай базу.

## Построение отчёта
Собери HTML из `assets/dashboard-template.html` (готовый пример на кампании 112538) — замени
данные на реальные, сохранив структуру и стиль. Опубликуй через Artifact (favicon 📈). При
первом использовании загрузи `artifact-design` — только ради технических требований к
публикации (см. «Вёрстка дашборда не меняется»).

### Вёрстка дашборда не меняется

`assets/dashboard-template.html` — готовая утверждённая вёрстка. Меняются **только данные**: числа, проценты,
даты, названия кампаний, списков и тем, подписи значений, количество строк в таблицах и
элементов в списках — по фактическим данным.

Запрещено:
- добавлять разделы, карточки, плашки, графики, таблицы, колонки, пояснительные абзацы, выводы
  и рекомендации, которых нет в шаблоне и которые не описаны в этом файле;
- удалять, переставлять и объединять разделы шаблона;
- менять CSS: цвета, палитру, шрифты, размеры, отступы, сетку, скругления, тени, анимацию;
- переименовывать заголовки разделов, подписи колонок и элементы интерфейса;
- подключать внешние библиотеки, скрипты, шрифты и картинки, которых нет в шаблоне;
- «улучшать» оформление по своему усмотрению, даже если кажется, что так нагляднее.

Скилл `artifact-design` загружай только ради технических требований к публикации. Его
рекомендации по дизайну к этому дашборду не применяются: дизайн уже задан шаблоном.

Если для раздела нет данных, не удаляй раздел и не придумывай ему замену: оставь его на месте с
пометкой «Нет данных», если в этом файле не сказано иначе.

Менять вёрстку можно только по прямой просьбе пользователя и только в том, о чём он попросил.

### Разделы отчёта (по порядку)
1. **Шапка: карточка рассылки** — это ОСНОВНАЯ информация, а не справочная мелочь, и она не
   должна быть простынёй текста. Оформи двумя ярусами:
   - **«письмо во входящих»**: аватар-бейдж отправителя, имя + email, дата справа; ниже тема
     крупным жирным, под ней прехедер серым — как строка в почтовом клиенте;
   - **ряд фактов** под разделителем, 4 колонки с вертикальными разделителями: «ID · тип»,
     «База» (главным — ЧИСЛО адресов, название списка подписью), «Отправка» (12:30 → 12:55 МСК,
     подписью длительность из startedAt/finishedAt), «Статус рассылки» (из `status`: completed →
     «Завершена ✓» зелёным, in_progress → «Идёт отправка», scheduled → «Запланирована»,
     banned → «Отклонена» красным; подписью статус модерации).
   Времена переводи в МСК и помечай. Не смешивай все поля в одну сетку без иерархии.
1a. **«Особенности рассылки»** (не «Задача») — краткий контекст письма (напр. n-е касание
   серии), без дублирования полей карточки.
2. **Итоги (KPI)** — Отправлено, Доставлено %, OR, CTOR, Отписки %, Жалобы, Ошибки %.
2a. **«База»** (сразу под Итогами) — карточка об аудитории отправки. Структура строгая, в две
   колонки с вертикальным разделителем (данные должны считываться глазом, не сливаться в текст):
   - **Левая колонка**: блок «Списки» — каждый список отдельным чипом в столбик (не в строку);
     длинные названия обрезаются `ellipsis` с полным именем в `title`, чипы не разваливают
     вёрстку. Ниже блок «Сегментация» — имя/условия сегмента или «Нет — отправка по всему списку».
   - **Правая колонка**: «Состав по почтовым системам» — СТРОКАМИ-таблицей, по строке на
     провайдера: логотип + имя | горизонтальная полоса (ширина от максимума, цвет провайдера) |
     % жирно | абсолют серым. НЕ стековая 100%-полоса с легендой — строки читаются лучше.
     Доли считай из `total` каждой группы `get_stats_by_domains` (сумма = отправленным),
     сортируй по убыванию.
   На мобильном колонки складываются вертикально.
3. **Воронка** — Отправлено → Доставлено → Открыто → Клик (число + % конверсии шага). Полосы
   **центрируй по общей оси** (`justify-content:center` у контейнера полосы), чтобы ступени
   сужались симметрично и форма читалась как воронка; полосы, прижатые к левому краю, выглядят
   обычной гистограммой.
4. **Динамика по дням** — **линейный график** из `get_activity` (он отдаёт `opens` И `clicks`
   по дням — рисуй ОБЕ линии, а не только открытия). Клики сильно меньше открытий → двойная ось,
   и обе оси ОБЯЗАНЫ иметь видимые шкалы со значениями: левая ось — открытия, правая (цветом
   линии кликов) — клики, с общими гридлайнами (напр. 0 / середина / максимум). Никогда не
   оставляй вторую серию без шкалы — о соразмерности нельзя заставлять догадываться. Временной
   ряд — линией, не столбиками; подпиши значения точек; отметь долю 1-го дня.
5. **По почтовым системам** — таблица с логотипами: OR, CTOR, отписки, ошибки по каждому.
6. **Куда кликали** — топ ссылок с долями. Название ссылки/раздела важнее его длины: колонка с
   названием должна сесть по содержимому (`grid-template-columns: max-content 1fr auto`,
   `white-space:nowrap` на названии) и НИКОГДА не переноситься — не подгоняй имя под
   фиксированную узкую колонку. Если название всё равно очень длинное, сокращай текст
   осмысленно (не обрезай серединой слова), а не сжимай колонку.
6a. **«Письмо · тепловая карта кликов»** — визуальная связка контента и результата. Получи шаблон
   через `templates_get_by_id(campaign.templateId)` и слева отрисуй **превью письма**: упрощённая
   реконструкция по реальным текстам/структуре/цветам шаблона (внешние картинки блокируются CSP —
   вместо них плейсхолдер-блок; честно подпиши, что это реконструкция). Кликабельные зоны
   (кнопки, логотип в шапке, ссылки в футере) подсвети рамкой+заливкой с интенсивностью по числу
   кликов и бейджем «N · %». Справа — шкала интенсивности и список зон (название | полоса |
   клики | доля). Сопоставляй URL из `get_link_clicks` с элементами шаблона — так видно, что
   именно кликают (частая находка: логотип в шапке собирает заметную долю кликов «мимо оффера»).
   Интенсивность строй на акцентном цвете (не красный).
7. **Доставляемость и риски** — **вердикт вынеси НАВЕРХ секции заметным баннером** (зелёный ok /
   амбер warn / красный — плохо), под ним плитки Доставка / Жалобы / Отписки. Пороги: норма
   отписок < ~0,3–0,5%, жалоб < ~0,1%, доставка > ~98%.

Отдельную секцию «Ключевые выводы» по умолчанию НЕ добавляй — итог по здоровью отправки несёт
баннер-вердикт в п.7, а продуктовые наблюдения давай в тексте ответа. Делай её, только если
пользователь прямо попросит.

### Обязательные принципы (общие для отчётов RuSender)
1. **Относительные метрики важнее абсолютных** — процент крупно и первым (акцентным цветом),
   абсолют тем же кеглем ниже.
2. **Воронку рисуй воронкой.**
3. **Логотипы почтовиков** — из `iconBase64` (`get_stats_by_domains`), как `<img>` data-URI.
4. **Красный не использовать в палитре полосок/провайдеров** — он читается как ошибка; провайдеры
   не-красными цветами (Gmail `#4285f4`, Yandex `#7b5cd6`, Mail.ru `#1a86e0`, прочие — серый).
   Красный оставь только для реальных проблем (в панели рисков — если показатель плохой).
6. **Не крась негативные метрики в зелёный.** Жалобы/ошибки/отписки в KPI — нейтральные (цвет
   текста), даже когда их 0: зелёный = «хорошо» и на негативной категории сбивает с толку.
   Зелёным помечай только реально позитивное (доставка) и вердикт «ok». Плохие значения —
   амбер/красный по порогу.
5. Адаптив, светлая/тёмная темы через токены, `tabular-nums`, нейтрально-синий акцент.

## Выводы
Разбери: уровень OR/CTOR относительно ожиданий (и относительно прошлых писем, если серия);
скорость затухания открытий; какой почтовик открывает/кликает лучше; куда шли клики (совпал ли
оффер с намерением); здоровье доставки (ошибки/отписки/жалобы) с вердиктом; 1–2 рекомендации
(частота, сегментация по почтовику, чистка ошибочных адресов).

## Ограничения
- Поимённых списков «кто открыл/кликнул/отписался/с ошибкой» и SMTP-ответов API не отдаёт —
  в дашборд идут только агрегаты и разрезы (по времени, домену, ссылке).
- Для составных (`follow_up_basic`) не забудь `totalStats`, иначе итог занижен.
