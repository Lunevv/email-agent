# RuSender: дашборд-отчёт по A/B-тесту

## Что делает
По одному id A/B-кампании (`type: ab_basic`) собирает всю доступную статистику и
публикует **единый визуальный отчёт-артефакт**: KPI, воронка, сравнение вариантов темы с
победителем, разбивка по почтовикам, матрица «тема × провайдер» и клики по ссылкам. Цель —
готовый к показу отчёт, а не сырые цифры.

## Инструменты (MCP RuSender)
Префикс сервера меняется при переподключении — не хардкодь его, загружай по именам через
ToolSearch: `public_campaigns_get_by_id`, `public_campaigns_get_link_clicks`,
`public_campaigns_get_stats_by_domains`, при необходимости `public_campaigns_list`,
`public_campaigns_get_activity`.

## Вход
- **id A/B-кампании**. Если пользователь дал имя — найди id через `public_campaigns_list`
  (`name`), убедись, что `type: ab_basic`. Если это не A/B (обычная/follow_up) — скажи и
  предложи обычный отчёт.

## Сбор данных

### 1. Структура и итоги — `get_by_id(campaignId, withStats:true)`
Для A/B ответ содержит:
- `abTest.variants[]` — по каждому варианту: `id`, `subject`, `splitPercent`, `isWinner`,
  `stats` (delivered, open, click, unsubscribe). Плюс `abTest.testPercent`, `winnerId`.
- `parent` — объект основной кампании (`ab_basic`); его `stats` = **досыл победителя на
  оставшуюся аудиторию** (не тестовые группы).
- `totalStats` — суммарно по всему тесту (тест + досыл).
> Вызывай `get_by_id` по id, который вернул `campaigns_list`. Если пришёл вариант, всё это
> лежит в нём же; если пришёл `ab_basic`-родитель — бери `abTest` из него.

### 2. Клики по ссылкам — `get_link_clicks` по КАЖДОЙ части
Вызови для каждого `variant.id` И для родителя (`parent.id` / основной досыл). Просуммируй
клики по каждой ссылке со всех частей. **Проверка:** сумма всех кликов должна равняться
`totalStats.click` — если нет, part пропущена. Сгруппируй ссылки в понятные категории
(документация, главная, конкретные разделы, квизы), а не сырые URL с utm.

### 3. Матрица «тема × провайдер» — `get_stats_by_domains` по КАЖДОМУ варианту
Для каждого `variant.id` вызови `get_stats_by_domains` — вернёт группы Gmail / Yandex /
Mail.ru / others с `total` и `open`. Посчитай OR = `open/total` по каждой ячейке. Дополнительно
вызови по родителю (досыл) — это отдельный столбец «Досыл победителя». Отметь ★ лучшую тему
для каждого провайдера **среди тестовых вариантов** (досыл — отдельно, другая аудитория).

## Метрики (не перепутай базы расчёта)
- **OR (открываемость)** = `open / delivered`.
- **CTOR** = `click / open` (в API это `click.rate`).
- **CTR** = `click / delivered`.
- В разбивке по доменам `open.rate` считается от `total` (отправленных группе) — считай OR
  как `open/total`, это нормально, подпиши явно.
- ⚠️ `totalStats.OR` делится на сумму отправок (тест + досыл), а не на уникальный охват. Для
  «честной» открываемости по людям: `(сумма open по вариантам + open досыла) / delivered
  основной аудитории`. В отчёте показывай `totalStats`, но упомяни этот нюанс в подвале.

## Построение отчёта
Собери HTML из шаблона `assets/dashboard-template.html` — это готовый пример нашего дашборда;
замени в нём данные на реальные по целевой кампании, сохранив структуру и стиль. Затем
опубликуй через инструмент Artifact (favicon 📊). При первом использовании
загрузи скилл `artifact-design` — только ради технических требований к публикации
(см. «Вёрстка дашборда не меняется»).

### Вёрстка дашборда не меняется

`assets/dashboard-template.html` — готовая утверждённая вёрстка. Меняются **только данные**: числа, проценты,
даты, названия кампаний, списков и тем, подписи значений, количество строк в таблицах и
элементов в списках — по фактическим данным.

Запрещено:
- добавлять разделы, карточки, плашки, графики, таблицы, колонки, пояснительные абзацы, выводы
  и рекомендации, которых нет в шаблоне и которые не описаны в этом файле;
- удалять, переставлять и объединять разделы шаблона;
- менять CSS: цвета, палитру, шрифты, размеры, отступы, сетку, скругления, тени, анимацию;
- переименовывать заголовки разделов, подписи колонок и элементы интерфейса;
- подключать внешние библиотеки, скрипты, шрифты и картинки, которых нет в шаблоне;
- «улучшать» оформление по своему усмотрению, даже если кажется, что так нагляднее.

Скилл `artifact-design` загружай только ради технических требований к публикации. Его
рекомендации по дизайну к этому дашборду не применяются: дизайн уже задан шаблоном.

Если для раздела нет данных, не удаляй раздел и не придумывай ему замену: оставь его на месте с
пометкой «Нет данных», если в этом файле не сказано иначе.

Менять вёрстку можно только по прямой просьбе пользователя и только в том, о чём он попросил.

### Обязательные принципы отчёта (выстраданы на практике)
1. **Относительные метрики важнее абсолютных.** В KPI процент (OR, CTOR, доставляемость)
   должен быть таким же крупным и жирным, как абсолют, и стоять первым (акцентным цветом).
2. **Воронку рисуй воронкой** (сужающиеся ступени Отправлено → Доставлено → Открыто → Клик),
   у каждой — и число, и % конверсии шага.
3. **Начинай с блока «Задача»**: что за тест, дата отправки, список тем (с пометкой
   победителя), механика сплита (testPercent, досыл победителя).
4. **В матрице разделяй источники данных**: столбцы A/B-теста (равные группы, темы сравнимы)
   и отдельный столбец «Досыл победителя» (большая аудитория, одна тема) — через визуальный
   разделитель и подписи с размерами групп. Не смешивай их в одну кучу.
5. **Клики — по всем частям** (сумма = `totalStats.click`), а не только по досылу. Явно
   подпиши охват («все части · N кликов»).
6. **Тема-победитель** берётся из `isWinner:true` (или `winnerId`), а не угадывается.
7. **Подвал** — источник (id кампании и вариантов), определения OR/CTOR, оговорки про малые
   сегменты (директивно, не статзначимо) и про базу расчёта `totalStats`.

### Оформление
Адаптив (перестройка на мобильном), светлая и тёмная темы (через CSS-токены), табличные
цифры (`tabular-nums`), брендовая магента RuSender как акцент, брендовые цвета провайдеров
для их графиков (Gmail #ea4335, Yandex #fc3f1d, Mail.ru #1a86e0, прочие — нейтральный).
Разметку и полный набор токенов бери из `assets/dashboard-template.html`.

## Выводы
Заверши отчёт разделом «Ключевые выводы»: какая тема победила и почему, как различается
реакция почтовиков (разрыв Gmail vs Yandex/Mail.ru — типичен), где единый победитель
недобрал (если по матрице у Gmail/Yandex лучшая тема иная), куда шли клики. Пиши по делу,
с конкретными числами.

## Ограничения (упомяни, если всплывут)
- Поимённого списка «кто открыл» API не даёт — сравнения на уровне людей делаются перебором
  истории по контактам (медленно), в дашборд не входят.
- Малые сегменты дают предупреждение о незначимости — не выдавай за точный вывод.
